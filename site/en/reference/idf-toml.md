# idf.toml

`idf.toml` is the only source of truth for a project. The project name, chip, ESP-IDF version, Kconfig settings, dependencies and partition table are all written here. At build time `idf` translates it into the CMake project, `sdkconfig.defaults`, `partitions.csv` and `idf_component.yml` under `build/`. The project directory does not need these upstream files, and should not contain them.

This page follows `src/manifest.rs`.

## Overview

| Table | Required | Description |
| --- | --- | --- |
| [`[project]`](#project) | Yes | Project name, chip, ESP-IDF version. |
| [`[config]`](#config) | No | Kconfig settings, shared by all profiles. |
| [`[dependencies]`](#dependencies) | No | Component dependencies. |
| [`[[partition]]`](#partition) | No | Partition table, in the order written. |
| [`[profile.<name>]`](#profile) | No | Configuration overrides for a profile. |

All tables reject unknown keys. An unknown top-level table is an error:

```text
unknown field `build`, expected one of `project`, `config`, `dependencies`, `partition`, `profile`
```

## Complete example

```toml
[project]
name = "blink"
target = "esp32s3"
idf = "6.0"

[config]
FREERTOS_HZ = 1000
LOG_DEFAULT_LEVEL_DEBUG = true
ESPTOOLPY_FLASHSIZE_4MB = true

[dependencies]
"espressif/led_strip" = "^3.0.1"
"espressif/mdns" = { version = "^1.2", targets = ["esp32", "esp32s3"] }
mylib = { git = "https://example.com/mylib.git", rev = "v1.0", subdir = "comp" }
local = { path = "../local" }

[[partition]]
name = "nvs"
type = "data"
subtype = "nvs"
size = "24K"

[[partition]]
name = "phy_init"
type = "data"
subtype = "phy"
size = "4K"

[[partition]]
name = "factory"
type = "app"
subtype = "factory"
offset = "64K"
size = "1M"

[profile.release.config]
COMPILER_OPTIMIZATION_PERF = true

[profile.ci.config]
FREERTOS_HZ = 100
```

The minimal file generated by `idf new` contains only `[project]`:

```toml
[project]
name = "blink"
target = "esp32s3"
idf = "6.0"
```

## Error messages

Every error in `idf.toml` is reported by miette with the file, line and column:

```text
Error: idf::invalid_file

  × ESP-IDF 5.3 is not supported by this idf-next
   ╭─[/path/to/blink/idf.toml:4:7]
 3 │ target = "esp32s3"
 4 │ idf = "5.3"
   ·       ──┬──
   ·         ╰── unsupported ESP-IDF release
   ╰────
  help: idf-next 0.1.0 supports ESP-IDF >=6.0.0, <6.1.0
```

TOML syntax errors, type errors, and missing required keys (such as ``missing field `idf` ``) are reported with the title `invalid idf.toml`. The specific cause is in the label. The messages for each validation rule are listed below.

The commands that modify `idf.toml` (`target set`, `sdk use`, `config set`, `config menu`, `add`, `remove`) edit it in place with toml_edit, preserving comments and formatting. The edited content passes the same validation before it is written to disk.

## [project] {#project}

| Key | Type | Required | Description |
| --- | --- | --- | --- |
| `name` | string | Yes | Project name. Used as the CMake `project()` name, so it also determines the file names of `<name>.elf`, `<name>.map` and other outputs. |
| `target` | string | Yes | Chip, such as `"esp32s3"`. |
| `idf` | string | Yes | ESP-IDF release series (`"6.0"`) or an exact version (`"6.0.1"`). |

### name

Must start with an ASCII letter. The rest may contain only ASCII letters, digits, `-` and `_`.

```text
× invalid project name
  ╰── not a valid project name
help: use letters, digits, `-` and `_`, starting with a letter
```

### target

Must be `esp32`, followed by zero or more lowercase letters or digits, for example `esp32`, `esp32s3`, `esp32c61`, `esp32p4`.

```text
"ESP32S3" is not a chip name; expected one like "esp32s3" (did you mean "esp32s3"?)
```

A name that has this form but is not in the known list (`idf target list`) is also accepted. The SDK decides whether it is supported. The known list is the non-preview chips of ESP-IDF v6.0: `esp32`, `esp32s2`, `esp32s3`, `esp32c2`, `esp32c3`, `esp32c5`, `esp32c6`, `esp32c61`, `esp32h2`, `esp32p4`.

The command-line option `-t/--target` can override it temporarily. It uses the same validation rules.

### idf

Only two forms are accepted:

- A release series `"major.minor"`, such as `"6.0"`. It matches any stable release `6.0.x` in that series.
- An exact version `"major.minor.patch"`, such as `"6.0.1"`.

A `v` prefix is allowed (`"v6.0.1"`). Semver constraints (`"^6.0"`, `">=6.0"`), wildcards and pre-release versions are not accepted. A pre-release version such as `6.0.0-rc1` is never matched. This is intentional: a project tracks one version, upgrading is an explicit action, and the exact version is pinned by [`idf.lock`](/en/reference/idf-lock).

```text
expected an ESP-IDF release like "6.0" or "6.0.1", got "^6.0"
```

The version must be within the range the tool supports (`>=6.0.0, <6.1.0` for 0.1.0). Otherwise the error `ESP-IDF 5.3 is not supported by this idf-next` is reported, as shown above.

Change this key with `idf sdk use <version>`, not by editing the file. That command installs the SDK and updates the lock at the same time.

## [config] {#config}

Kconfig settings. Each key is a Kconfig symbol name, and each value is the value of that symbol. The settings apply to all profiles. Profile overrides are described in [`[profile.<name>]`](#profile). The default is an empty table.

### Keys

- Do not include the `CONFIG_` prefix. Write `FREERTOS_HZ`, not `CONFIG_FREERTOS_HZ`.
- May contain only uppercase letters, digits and `_`. Must not start with a digit. Must not be empty.

```text
drop the CONFIG_ prefix: write "FREERTOS_HZ"
"freertos_hz" is not a Kconfig symbol; expected UPPER_SNAKE_CASE
```

`idf.toml` does not check whether a symbol exists. That check is done at build time (see below).

### Values

| TOML type | Kconfig type | Written to `sdkconfig.defaults` |
| --- | --- | --- |
| Boolean | `bool` | `true` gives `CONFIG_X=y`; `false` gives `# CONFIG_X is not set` |
| Integer | `int` | `CONFIG_X=1000` |
| String of the form `"0x…"` | `hex` | Written as is, such as `CONFIG_X=0x9000` |
| Other string | `string` | Quoted, with `\` and `"` escaped, such as `CONFIG_X="say \"hi\""` |

Other types (floating-point numbers, arrays, tables) are an error: ``a boolean, an integer or a string``.

::: warning Write hex values as strings
Kconfig always reads `hex` symbols as hexadecimal, even without a `0x` prefix. So the integer `4096` is read as `0x4096`. Write hex symbols as strings: `PARTITION_TABLE_OFFSET = "0x9000"`. `idf config set` writes them this way automatically.
:::

### choice

A Kconfig choice cannot be assigned directly. To select an option, set it to `true`:

```toml
[config]
LOG_DEFAULT_LEVEL_DEBUG = true    # not LOG_DEFAULT_LEVEL = "debug"
```

`idf config set LOG_DEFAULT_LEVEL=debug` writes the form above and removes the other options of the same choice.

### Build-time checks

Each time CMake configuration runs again, `idf build` checks the `[config]` table and the overrides of the current profile. It reports the following as warnings. It does not stop the build:

- Unknown keys, with close matches suggested;
- A value assigned to a choice itself;
- A symbol with no prompt. Its value is determined by Kconfig from other options;
- A value that was written but has no effect (dependency not enabled, prompt hidden, selected by another symbol, out of range), with the reason.

### Relation to sdkconfig

`[config]` only generates `sdkconfig.defaults`. `sdkconfig` is located in the build directory, at `build/<target>/<profile>/sdkconfig`. When `sdkconfig.defaults` changes, `idf build` deletes the old `sdkconfig` and regenerates it. IDF defaults only fill in values missing from `sdkconfig`, and `idf.toml` is the only source of truth.

## [dependencies] {#dependencies}

Component dependencies. Each key is a component name. Each value is a version requirement string or a table. The default is an empty table.

```toml
[dependencies]
"espressif/led_strip" = "*"
"espressif/mdns" = { version = "^1.2", targets = ["esp32", "esp32s3"] }
mylib = { git = "https://example.com/mylib.git", rev = "v1.0", subdir = "comp" }
local = { path = "../local" }
```

### Keys

- Registry dependencies are written as `namespace/name`. They must be quoted, because a bare TOML key cannot contain `/`.
- Git and path dependencies can use any name. However, a path dependency should have the same name as its component directory. The component manager looks up components by directory name, and `idf add --path` enforces this.

### Values

The string form is equivalent to `{ version = "<string>" }`. Keys of the table form:

| Key | Type | Description |
| --- | --- | --- |
| `version` | string | Version requirement for the registry. It is passed to the component manager unchanged, and the component manager determines the syntax. |
| `git` | string | Git repository URL. |
| `rev` | string | Git branch, tag or commit. Only for `git`. |
| `subdir` | string | Subdirectory of the component within the repository. Only for `git`. |
| `path` | string | Local component directory, relative to the project root or absolute. |
| `targets` | array of chip names | Only add the dependency for these chips. Must not be an empty array. |
| `idf` | string | Only add the dependency for this ESP-IDF version. The format is the same as `[project] idf`. |

Exactly one of `version`, `git` or `path` must be given. Validation errors:

| Case | Error |
| --- | --- |
| None of the three is given | ``a dependency needs one of `version`, `git` or `path` `` |
| More than one is given | ``use only one of `version`, `git` or `path` `` |
| `rev` or `subdir` used on a non-git dependency | ``` `rev` and `subdir` only apply to `git` dependencies ``` |
| `version`, `git` or `path` is an empty string | ``` `version` is empty ``` (the name of the field) |
| `targets = []` | ``` `targets` is empty; remove it or list at least one chip ``` |
| Other keys | `unknown field ...` |

### Translation to the component manager's manifest

At build time, `[dependencies]` is written to the generated `build/<target>/<profile>/project/main/idf_component.yml`:

| `idf.toml` | `idf_component.yml` |
| --- | --- |
| `version = "^1.2"` (no conditions) | `"^1.2"` |
| `targets = ["esp32", "esp32s3"]` | `rules: [{ if: "target in [esp32, esp32s3]" }]` |
| `idf = "6.0"` | `rules: [{ if: "idf_version >=6.0.0,<6.1.0" }]` |
| `idf = "6.0.1"` | `rules: [{ if: "idf_version ==6.0.1" }]` |
| `git` / `rev` / `subdir` | `git` / `version` / `path`. The commit pinned in `idf.lock` takes precedence over `rev`. |
| `path` | `path` with an absolute path |

When there are no dependencies, no manifest is generated and the component manager does not run. The resolution result is recorded in the `[[component]]` entries of `idf.lock`. See [idf.lock](/en/reference/idf-lock#component). For usage, see [Dependencies](/en/guide/dependencies).

## [[partition]] {#partition}

The partition table. It is written as an array of tables, so that the order is preserved. Without any `[[partition]]`, the SDK's default partition table configuration is used.

| Key | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `name` | string | Yes | | 1 to 15 ASCII characters, unique within the table. |
| `type` | string | Yes | | Such as `"app"` or `"data"`. Written to the CSV unchanged. |
| `subtype` | string | Yes | | Such as `"factory"`, `"nvs"` or `"phy"`. Written to the CSV unchanged. |
| `size` | size | Yes | | Partition size. |
| `offset` | size | No | Empty | If omitted, the partition follows the previous one. gen_esp32part calculates the offset according to its alignment rules. |
| `encrypted` | boolean | No | `false` | The `encrypted` flag in the CSV. |
| `readonly` | boolean | No | `false` | The `readonly` flag in the CSV. |

### Size formats

`size` and `offset` accept:

- A non-negative integer: `4096`;
- A decimal string: `"4096"`;
- A hexadecimal string: `"0x1000"` (`0x` or `0X`);
- A string with a suffix: `"24K"` (×1024) or `"1M"` (×1048576). The suffix is case-insensitive.

A hexadecimal value cannot have a suffix. `"0x10K"` is invalid.

```text
"24Q" is not a size; use bytes, "0x…", "24K" or "1M"
size cannot be negative
```

### Name validation

```text
× invalid partition name
  ╰── must be 1–15 ASCII characters

× duplicate partition "nvs"
  ╰── already defined on line 7
help: partition names must be unique
```

`idf.toml` only checks names. `type`, `subtype`, offsets and alignment are checked at build time by IDF's `gen_esp32part.py`.

### Generated files

The example above generates `build/<target>/<profile>/project/partitions.csv`:

```text
# Generated by idf from idf.toml. Do not edit.
# Name, Type, SubType, Offset, Size, Flags
nvs, data, nvs, , 0x6000,
phy_init, data, phy, , 0x1000,
factory, app, factory, 0x10000, 0x100000,
```

Two lines are also appended to the end of `sdkconfig.defaults`:

```text
CONFIG_PARTITION_TABLE_CUSTOM=y
CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions.csv"
```

These two lines come after `[config]`, so the custom partition table is always used when `[[partition]]` is present.

## [profile.&lt;name&gt;] {#profile}

A profile is a set of configuration that is layered on top of `[config]`. Each profile has its own build directory, `build/<target>/<profile>/`.

| Key | Type | Required | Description |
| --- | --- | --- | --- |
| `config` | table | No | Same rules as `[config]`. A key with the same name overrides the value from `[config]`. |

Only `config` is allowed under `[profile.<name>]`. Any other key is an error: ``unknown field `foo`, expected `config` ``.

### Selecting a profile

| Command line | Profile |
| --- | --- |
| Default | `dev` |
| `-r` / `--release` | `release` |
| `--profile <NAME>` | `<NAME>` |

`dev` and `release` are built in. They can be used without being declared. Any other name must be declared in `idf.toml`. It can be an empty table (`[profile.ci]`). Otherwise an error is reported:

```text
no profile named `ci`
help: Built-in profiles are `dev` and `release`; others are declared as [profile.<name>] in idf.toml.
```

::: tip The release profile has no implicit configuration
The built-in `release` profile does not change any Kconfig value. It is only a separate build directory, plus the overrides you write in `[profile.release.config]`. Write any optimization options you need yourself, for example `COMPILER_OPTIMIZATION_PERF = true`.
:::

When `idf config set` and `idf config menu` are given a profile explicitly on the command line (`-r` or `--profile`), they write to `[profile.<name>.config]`. Otherwise they write to `[config]`.

## What is not in idf.toml

- **Serial port and baud rate**: these depend on the machine. They are set with `-p`, `IDF_PORT` or `~/.config/idf/config.toml`. See [Environment variables and user config](/en/reference/environment).
- **Exact SDK version, toolchain and dependency versions**: pinned by `idf.lock`.
- **Source file list**: all `.c`, `.cc`, `.cpp`, `.cxx`, `.S` and `.s` files under `src/` (recursively, skipping files and directories that start with `.`) are included automatically in the `main` component. The header directory is `src/`. `src/Kconfig` and `src/Kconfig.projbuild` are referenced as the Kconfig of the `main` component. The project's `components/` directory, if it exists, is used as an extra component directory.

::: warning Not supported yet
The `EMBED_FILES` / `EMBED_TXTFILES` settings of the `main` component and custom CMake logic cannot currently be expressed in `idf.toml`. Code that needs them can be placed in a component under `components/`, using that component's own `CMakeLists.txt`.
:::
