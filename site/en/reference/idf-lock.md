# idf.lock

`idf.lock` pins everything in the project that `idf.toml` leaves to the tool to decide. This covers the exact ESP-IDF version and commit, the hash of the source tree, the Python interpreter and resolution result, the hash of each toolchain archive, and the versions and hashes of component dependencies. `idf` generates it. It should be committed to the repository and not edited by hand.

`idf.lock` is independent of the version of idf-next itself. Any change to a pinned item is an explicit action. This page follows `src/lockfile.rs`.

## Example

Below is the `idf.lock` of a project using ESP-IDF 6.0.3. Only one `[[tool]]` is kept (there are 9 in total). The two `[[component]]` entries are illustrative.

```toml
# This file is generated by idf. Do not edit it by hand.

version = 1

[idf]
version = "6.0.3"
commit = "76f5dedd9950a3012fee8fb7d5586df21fc67802"
source = "sha256:f05f147670925e64d019f216292b6db49234d7619a0d0ce915cf0aa56432da16"

[python]
version = "3.12.13"
exclude-newer = "2026-11-13T14:33:15Z"
constraints = "sha256:a5bdbb070fde39267479e4b38dc0110aa7df9342e9d13b6b4cfc9b7537641774"
requirements = "sha256:14645654ec2ff38cf6bf9c220c1ef83eeb05d0fba1136642971d7f8293290abd"

[[tool]]
name = "cmake"
version = "4.0.3"

[tool.archives.linux-amd64]
url = "https://github.com/Kitware/CMake/releases/download/v4.0.3/cmake-4.0.3-linux-x86_64.tar.gz"
sha256 = "585ae9e013107bc8e7c7c9ce872cbdcbdff569e675b07ef57aacfb88c886faac"
size = 55509479

[tool.archives.linux-arm64]
url = "https://github.com/Kitware/CMake/releases/download/v4.0.3/cmake-4.0.3-linux-aarch64.tar.gz"
sha256 = "391da1544ef50ac31300841caaf11db4de3976cdc4468643272e44b3f4644713"
size = 56811927

[tool.archives.macos-arm64]
url = "https://github.com/Kitware/CMake/releases/download/v4.0.3/cmake-4.0.3-macos-universal.tar.gz"
sha256 = "4e85de4daf1c3e82d7dc6b8ba5683972944b466343aeb9c327a742437bb3ce9a"
size = 80058792

[[component]]
name = "espressif/led_strip"
version = "3.0.1"
source = "registry+https://components.espressif.com/"
hash = "sha256:<64 hex digits>"

[[component]]
name = "local"
version = "0.1.0"
source = "path+components/local"
```

## Fields

All tables reject unknown keys.

### Top level

| Key | Type | Description |
| --- | --- | --- |
| `version` | integer | Version of the lock file format. The current value is `1`. It is incremented only when the format changes in an incompatible way. |

`idf` reads this field first, before parsing the rest. This way a different format version gives a clear error, and not "unknown field":

| Case | Error |
| --- | --- |
| No `version` | ``idf.lock has no `version` `` |
| Not `1` | `unsupported idf.lock format version 2`, with the label `this idf reads version 1` and the help `the lock file was written by a different idf-next; use a matching version` |

### [idf] {#idf}

| Key | Type | Description |
| --- | --- | --- |
| `version` | semver string | The exact ESP-IDF version, such as `"6.0.3"`. Must match `[project] idf` in `idf.toml`, and must be within the range the tool supports. |
| `commit` | 40 lowercase hexadecimal characters | The commit that the release tag of this version points to. |
| `source` | `"sha256:<64 lowercase hexadecimal characters>"` | The digest of the extracted source tree. |

If the version is outside the supported range, the error `idf.lock pins ESP-IDF 5.4.0, which this idf-next does not support` is reported.

The SDK source comes from the official release zip, which does not contain `.git`. `source` is the digest computed over the whole extracted source tree. It is compared with the lock at installation time.

### [python] {#python}

| Key | Type | Description |
| --- | --- | --- |
| `version` | semver string | The exact interpreter version that uv installs into the SDK venv. New resolutions use the 3.12 series by default. |
| `exclude-newer` | RFC 3339 time | The cutoff time passed to `uv pip compile --exclude-newer`. It makes resolving the same inputs again produce the same result. |
| `constraints` | `"sha256:…"` | Digest of the Espressif constraints file (`espidf.constraints.v<series>.txt`) used for resolution. |
| `requirements` | `"sha256:…"` | Digest of the full resolved requirements text, with hashes. |

The inputs to resolution are all non-optional requirements files listed in the SDK's `tools/requirements.json`, together with Espressif's constraints file. The command is `uv pip compile --universal --generate-hashes`, and only PyPI is used. The venv directory is named after the first 16 hexadecimal characters of the `requirements` digest (`~/.idf-next/sdk/<version>/python/<first 16 characters>/`). As a result, projects whose resolutions differ under the same SDK version do not share a venv.

### [[tool]] {#tool}

One entry for each toolchain package.

| Key | Type | Description |
| --- | --- | --- |
| `name` | string | Tool name, matching `tools/tools.json` in the SDK, such as `xtensa-esp-elf`. |
| `version` | string | Tool version, such as `esp-15.2.0_20251204`. |
| `archives` | table | Host platform → archive. |

`[tool.archives.<platform>]`:

| Key | Type | Description |
| --- | --- | --- |
| `url` | string | Download address. |
| `sha256` | 64 lowercase hexadecimal characters | SHA-256 of the archive, matching the value recorded in `tools.json`. |
| `size` | integer | Size of the archive in bytes. |

The platform keys are `macos-arm64`, `linux-amd64` and `linux-arm64`. The lock records the archives for all three platforms, so a lock written on one machine also works on another platform. The tool set is the tools in `tools.json` marked `install: always` for that platform, plus `cmake` and `ninja`. `idf` does not depend on the CMake and Ninja installed on the system. For ESP-IDF 6.0.3 on macOS arm64, there are 9 tools: `cmake`, `esp-rom-elfs`, `esp32ulp-elf`, `ninja`, `openocd-esp32`, `riscv32-esp-elf`, `riscv32-esp-elf-gdb`, `xtensa-esp-elf` and `xtensa-esp-elf-gdb`.

### [[component]] {#component}

One entry for each component resolved by the component manager, excluding ESP-IDF itself. Indirect dependencies are included. If there are no dependencies, there are no entries.

| Key | Type | Required | Description |
| --- | --- | --- | --- |
| `name` | string | Yes | Component name, such as `espressif/led_strip`. |
| `version` | string | Yes | The resolved version. For a git dependency, this is the commit hash. |
| `source` | string | Yes | Where the component comes from. See the table below. |
| `hash` | `"sha256:…"` | No | Hash of the downloaded component content (the component manager's `component_hash`). Present only for registry dependencies. |

`source` follows the notation used in Cargo.lock:

| Source | Format |
| --- | --- |
| Registry | `registry+<registry URL>` |
| Git | `git+<repository URL>#<40-character commit hash>` |
| Local path | `path+<path relative to the project root>` |

Any other format is an error: `... is not a source; expected registry+URL, git+URL#COMMIT or path+PATH`.

## Write behavior

- The file begins with the fixed comment line `# This file is generated by idf. Do not edit it by hand.`
- Serialization is deterministic. `[[tool]]` entries are sorted by name. `[[component]]` entries are sorted by name, then by source. The same content always produces a byte-identical file.
- Writes are atomic. The content is first written to `idf.lock.tmp`, then renamed to `idf.lock`. An interruption does not leave a truncated file.

## When it is rewritten

### SDK part: `[idf]`, `[python]`, `[[tool]]`

Commands that need the SDK (see [Commands](/en/reference/commands#needs-project)) first check the "current lock". A current lock is an `idf.lock` that exists and whose `[idf] version` matches `[project] idf` in `idf.toml`.

- **A current lock exists**: install exactly what the lock specifies (use it directly if already installed). The lock is not rewritten.
- **No lock, or the lock does not match `idf.toml`**: resolve the latest stable version matching `idf.toml` (queries GitHub when online; with `--offline`, uses the latest matching version already installed), install it, then rewrite the SDK part. Existing `[[component]]` entries are kept.

The following behaviors follow from this:

- When `idf = "6.0"` and the lock pins `6.0.3`, the lock stays in effect. Even if upstream publishes 6.0.4, there is no automatic upgrade.
- To upgrade to a new version, use `idf sdk use 6.0.4`. It changes `idf.toml` to `idf = "6.0.4"`. The lock no longer matches, so it is resolved again and pinned.
- Changing only the `idf` key in `idf.toml` by hand also triggers re-pinning, at the next command that needs the SDK. The difference with `idf sdk use` is that the latter also completes the installation.
- `idf sdk install <version>` only installs. It does not write the lock of any project.

### Dependency part: `[[component]]`

- **After `idf build` reconfigures**: reads the `dependencies.lock` that the component manager wrote in the build directory, and merges the names, versions, sources and hashes into `[[component]]`. If the result is the same as the existing content, no file is written.
- **`idf add`, `idf remove`**: after `idf.toml` is changed, dependencies are resolved again and `[[component]]` is updated.
- **`idf update [name…]`**: first removes the components to be updated from the lock (all of them, or the named ones together with the indirect dependencies that were pulled in only by them). Then resolves again.
- **`[dependencies]` is emptied**: the next build clears `[[component]]`.

`[[component]]` also determines the versions used by the build. Before configuration, a new build directory (for example, a freshly cloned repository) gets a `dependencies.lock` without `manifest_hash`, written by `idf` from the lock. The component manager therefore resolves again, but starts from these versions. The versions and hashes of registry dependencies do not drift as a result.

- **Git dependencies** cannot be pre-seeded this way, because the component manager re-resolves branches on every resolution. Instead, `idf` writes the commit from the lock into the `version` of the generated manifest. The `rev` in `idf.toml` is left unchanged.
- **Path dependencies** are read directly from disk and do not need to be locked.

::: warning Known limitations
- The first configuration of a new build directory still needs network access. Without `manifest_hash`, the component manager must resolve, and it needs to read registry metadata.
- For dependencies with `targets` restrictions, `[[component]]` is the union of the resolution results for each chip. A build for a different chip only adds entries. It does not remove the entries for other chips.
:::

## --locked {#locked}

`--locked` makes any operation that would rewrite `idf.lock` fail with an error. It is intended for CI and reproducible builds. It does not forbid network access. For fully offline operation, use it together with `--offline`.

| Scenario | Behavior |
| --- | --- |
| The SDK is needed, but there is no `idf.lock` | Error `idf.lock is missing, and --locked forbids updating it`, before any download |
| `idf.lock` does not match the `idf` key in `idf.toml` | Error `idf.lock does not match idf.toml, and --locked forbids updating it` |
| After the build, the component resolution differs from `[[component]]` | Error `the dependencies in idf.toml no longer match idf.lock, and --locked forbids updating it`, with a hint to run `idf update` (or build without `--locked`) and commit `idf.lock` |
| `idf add`, `idf remove`, `idf update` | Error `` `idf <command>` would change idf.toml and idf.lock, but --locked was given `` |
| `idf sdk use <version>` would need to change `idf.toml` | Error `` `idf sdk use` would change idf.toml, but --locked was given `` |
| The lock is complete and matches | Runs normally |

```bash
# Remove the SDK, then reinstall it offline from the lock. The result is byte-identical to the one before removal (the gate for P1)
idf sdk remove 6.0.3
idf --offline --locked sdk install
```

Offline reinstallation depends on the download cache under `~/.idf-next/` (`downloads/`), the interpreters managed by uv (`python/`), and uv's wheel cache (`uv-cache/`). `idf sdk remove` only deletes `sdk/<version>/`. It does not touch these three.

## Verification when installing from the lock

With or without `--locked`, installing from the lock checks each item and reports an error on any mismatch. It never silently rewrites the lock:

| Check | Error on mismatch |
| --- | --- |
| The `[idf]` of the installed SDK differs from the lock | `` the installed ESP-IDF 6.0.3 (<commit>) differs from idf.lock (<commit>); remove it with `idf sdk remove 6.0.3` `` |
| Digest of the extracted source tree | `ESP-IDF 6.0.3 source does not match idf.lock`, listing the digests on both sides |
| The SDK's `tools.json` against the `[[tool]]` entries for the local platform | `the SDK's tools.json does not match the tools in idf.lock for macos-arm64; the lock may be from another idf-next version` |
| sha256 and size of an archive | Download verification fails |
| Constraints file (not in the cache, downloaded again) | `` Espressif's constraints file for ESP-IDF 6.0 changed since idf.lock was written, and the original is not in the download cache. Run `idf sdk use` to re-pin. `` |
| Python dependencies resolved again (when the resolution is not in the cache) | `resolving the Python environment again gave a different result than idf.lock records`, with a hint that upstream inputs have changed; use `idf sdk use` to pin again |

Resolution results and constraints files are stored in the download cache, keyed by digest. As long as the cache exists, resolution does not need to be run again.
