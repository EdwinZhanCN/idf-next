# Project and idf.toml

`idf.toml` is the only source of truth for a project. From it, `idf` generates the CMake project that IDF needs, `sdkconfig.defaults`, the partition table, and the component manifests. All generated files go into `build/`.

## Project directory

```text
blink/
├── idf.toml                 # written by hand
├── idf.lock                 # generated by idf, commit to version control
├── src/                     # source code of the main component
├── components/              # optional: components of your own
├── build/                   # generated output, do not commit
└── compile_commands.json    # symbolic link to the most recent build, do not commit
```

`CMakeLists.txt`, `sdkconfig`, `idf_component.yml`, `dependencies.lock`, and `managed_components/` do not appear in the project. The `.gitignore` generated by `idf new` ignores `/build/` and `/compile_commands.json`.

`idf` looks for `idf.toml` in the current directory, or in the directory given by `-C`, and then in each parent directory. Commands can therefore be run from a subdirectory of `src/`.

### src/

`src/` is the generated `main` component:

- Files with the extensions `.c`, `.cc`, `.cpp`, `.cxx`, `.S`, and `.s` are collected recursively from `src/`. Files and directories whose names start with `.` are skipped. There must be at least one source file, and one of them must define `void app_main(void)`.
- `src/` itself is the header directory (`INCLUDE_DIRS`).
- `src/Kconfig` and `src/Kconfig.projbuild` are included in the `main` component. `rsource` statements inside them are still resolved relative to `src/`.

### components/

When a `components/` directory exists, it is set as `EXTRA_COMPONENT_DIRS`. Each subdirectory is treated as a component in the usual IDF way, with its own `CMakeLists.txt`.

::: warning Not supported yet
There is currently no way to express `EMBED_FILES` / `EMBED_TXTFILES` or custom CMake logic for the `main` component. Code that needs these can go into a component under `components/`, using that component's own `CMakeLists.txt`.
:::

## idf.toml

```toml
[project]
name = "blink"
target = "esp32s3"
idf = "6.0"

[config]
FREERTOS_HZ = 1000

[dependencies]
"espressif/led_strip" = "*"

[[partition]]
name = "nvs"
type = "data"
subtype = "nvs"
size = "24K"

[[partition]]
name = "factory"
type = "app"
subtype = "factory"
size = "1M"

[profile.release.config]
COMPILER_OPTIMIZATION_PERF = true
```

At the top level, only the sections `[project]`, `[config]`, `[dependencies]`, `[[partition]]`, and `[profile.*]` are allowed. All tables reject unknown keys. When there is an error, `idf` reports the line and column where it occurred.

### [project]

| Key | Description |
| --- | --- |
| `name` | Project name. Starts with a letter and contains only letters, digits, `-`, and `_`. It is also the file name of the generated ELF, bin, and map files |
| `target` | Chip name, such as `esp32s3`. `idf target list` lists the non-preview chips of ESP-IDF 6.0. Other names of the form `esp32…` are also accepted and left for the SDK to judge |
| `idf` | Release series `"6.0"`, or an exact version `"6.0.3"`. Arbitrary semver ranges are not accepted. A version outside the range supported by the tool is an error |

`target` can be overridden temporarily with `-t`, and written back to `idf.toml` with `idf target set <chip>`. `idf` edits the file with toml_edit, so comments and formatting are preserved. To change the IDF version of `idf`, use `idf sdk use <version>`; see [SDK and environment](/en/guide/sdk).

### [config]

Kconfig options. Keys have no `CONFIG_` prefix. Values are booleans, integers, or strings:

```toml
[config]
FREERTOS_HZ = 1000
LOG_DEFAULT_LEVEL_DEBUG = true     # choice: write the option that is selected
PARTITION_TABLE_OFFSET = "0x9000"  # hex type: write as a "0x…" string
```

If you write `CONFIG_FOO`, `idf` reports an error and suggests removing the prefix. Hex values must be written as `"0x…"` strings, because Kconfig always reads the digits of hex symbols as hexadecimal, so `4096` would be read as `0x4096`. For choices, type checking, and the checks performed at build time, see [Configuration](/en/guide/config).

### [profile.\<name\>.config]

Overrides applied on top of `[config]`. `dev` and `release` are built-in profiles and can be used without being declared. The default is `dev`. `-r` / `--release` selects `release`, and `--profile <name>` selects any name. A custom name must have a matching `[profile.<name>]` in `idf.toml`, or `idf` reports an error. Profiles currently have only one subtable, `config`.

```toml
[profile.release.config]
COMPILER_OPTIMIZATION_PERF = true
```

Each target and profile has its own build directory. Switching profiles does not cause the other profile to be reconfigured.

### [dependencies]

Component dependencies, from three kinds of source: registry, git, and local path. Conditional dependencies by chip or IDF version are also supported. See [Dependencies](/en/guide/dependencies).

### [[partition]]

The partition table. It is written as an array, and the order of the entries is the order of the partitions.

| Key | Description |
| --- | --- |
| `name` | 1 to 15 ASCII characters, unique within the table |
| `type` | For example `app` or `data` |
| `subtype` | For example `factory`, `nvs`, or `phy` |
| `size` | Size |
| `offset` | Optional. If omitted, the partition follows the previous one (with alignment) |
| `encrypted` | Optional, default `false` |
| `readonly` | Optional, default `false` |

`size` and `offset` can be written as integers (bytes), as `"0x…"`, or as decimal numbers with a `K` or `M` suffix (`"24K"`, `"1M"`). Hexadecimal with a suffix, such as `"0x10K"`, is not accepted.

When `[[partition]]` is present, `idf` generates `partitions.csv`, and appends `PARTITION_TABLE_CUSTOM=y` and the matching file name to the end of `sdkconfig.defaults`. The partition table in `idf.toml` is therefore always in effect. If `[[partition]]` is absent, IDF's default partition table is used.

## idf.lock

`idf.lock` pins everything that `idf.toml` does not fix in place. It is independent of the version of the `idf` tool itself. The file starts with a comment saying it was generated by `idf`. Do not edit it by hand.

```toml
version = 1

[idf]
version = "6.0.3"
commit = "76f5dedd9950a3012fee8fb7d5586df21fc67802"
source = "sha256:…"          # digest of the extracted source tree

[python]
version = "3.12.13"
exclude-newer = "2026-11-13T14:33:15Z"
constraints = "sha256:…"     # Espressif's constraints file
requirements = "sha256:…"    # the resolved dependency set, with hashes

[[tool]]
name = "cmake"
version = "4.0.3"

[tool.archives.macos-arm64]
url = "https://github.com/Kitware/CMake/releases/download/v4.0.3/cmake-4.0.3-macos-universal.tar.gz"
sha256 = "…"
size = 80058792
```

- `[[tool]]` records the archive for each tool on three platforms: macos-arm64, linux-amd64, and linux-arm64. The same lock file therefore works on another machine.
- `[[component]]` records the name, version, source, and hash of third-party components. See [Dependencies](/en/guide/dependencies).
- When the `idf` version in `idf.toml` does not match the version in the lock file, the lock is treated as stale. The next command that needs the SDK locks it again. With `--locked`, this is an error instead.
- Upgrades are explicit actions: `idf sdk use` changes the IDF version, and `idf update` changes component versions.

For a full description of each field, see the [idf.lock reference](/en/reference/idf-lock).

## What is in build/

Each target and profile has one directory, `build/<target>/<profile>/`, which is itself a CMake binary directory:

```text
build/esp32s3/dev/
├── project/                  # generated CMake source directory
│   ├── CMakeLists.txt        # sets SDKCONFIG and so on, and includes IDF's project.cmake
│   ├── main/CMakeLists.txt   # lists the source files under src/ using absolute paths
│   ├── main/idf_component.yml  # present when [dependencies] is set
│   ├── sdkconfig.defaults    # [config] plus the current profile
│   ├── partitions.csv        # present when [[partition]] is set
│   ├── dependencies.lock     # lock written by the component manager
│   └── managed_components/   # components downloaded by the component manager
├── sdkconfig
├── config/                   # kconfgen output (sdkconfig.json, kconfig_menus.json, and so on)
├── blink.elf  blink.bin  blink.map
├── flasher_args.json
└── ...
```

- A generated file is not rewritten if its content has not changed. Ninja decides by itself what needs to be recompiled.
- When `sdkconfig.defaults` changes, `sdkconfig` is deleted and regenerated. IDF's defaults only fill in values missing from sdkconfig. `idf.toml` is the source of truth.
- `idf clean` deletes the directory for the current target and profile. `idf clean --all` deletes the whole `build/` directory and removes the stale `compile_commands.json` link.

::: warning Git warnings in build output
The SDK is extracted from the release zip and has no `.git` directory, so CMake output contains `git rev-parse returned 'fatal: not a git repository'` and `Could not use 'git describe' to determine PROJECT_VER`. These do not affect the build. Without git, IDF reads the `version.txt` that `idf` writes.
:::
